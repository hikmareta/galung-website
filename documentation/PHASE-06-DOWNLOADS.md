## Storage prerequisites

Configure DOWNLOAD_S3_* server-only variables and DOWNLOAD_ARCHITECTURES from actual approved builds. Empty architecture configuration rejects all upload creation. There are no assumed x64/ARM/universal builds. Extensions are EXE/MSI for Windows and DMG/PKG for macOS, filenames use a restricted ASCII allowlist and size is 1–999,999,999 bytes.

The bucket must be private, versioning enabled, with HTTPS and no public listing or anonymous object reads. Version IDs must be returned by CompleteMultipartUpload and accepted by HeadObject/GetObject. Providers without these semantics are unsupported by this adapter; do not disable the check. CMS media storage is separate and unchanged.

Least-privilege application credentials: multipart create/upload/list/complete/abort, GetObject/GetObjectVersion and HeadObject on the installer prefix only; no public ACL mutation, bucket policy changes, bucket deletion or object-version deletion. Provider-specific IAM mapping must be verified before activation. Bucket policy should restrict transport and object size where supported. Configure storage lifecycle to abort incomplete multipart uploads after one day and monitor orphan completed objects; never expire referenced verified versions. CORS: exact admin site origin, PUT only (GET/HEAD only if needed by provider), Content-Type/required signed headers; expose ETag if required. Browser code does not need storage credentials or bucket-list permissions.

## Admin workflow

1. Super Admin saves a Galung software release draft with unique semantic version and channel. Other CMS roles cannot manage releases/assets. Upload controls appear on the saved release editor.
2. Choose Windows/macOS, an approved actual architecture, installer and expected lowercase SHA-256 from trusted build output. POST /api/installers begins a random isolated object key, bound to the authenticated admin, release, filename, expected size/hash, and a one-hour session.
3. Browser requests each 8 MiB part URL (five-minute expiry), then PUTs that slice directly to storage. The UI shows completed-part progress, retry and cancellation. Retry first checks server status without accessing storage. A completed upload reports success; a pending upload resumes at the next unconfirmed part or retries completion after all parts were sent. Busy 409 and ambiguous failures preserve the session; confirmed expired/aborted/failed sessions permit replacement. It does not persist state across a browser reload. Metadata/file controls stay locked during retries. App JSON bodies are limited to 32 KiB, including streamed requests; no binary upload endpoint exists.
4. Completion lists storage parts independently and checks consecutive part numbers and exact expected lengths. Only the server completes the multipart upload and records its immutable object version. Concurrent operations use a renewable, token-scoped PostgreSQL KV lease without holding a database connection during storage IO. An overlapping request returns retryable 409; replayed successful completion returns current state. Verification renews its ten-minute lease during streaming and checks ownership before state changes.
5. Operator runs `pnpm downloads:verify` separately from the web process. It streams private versioned storage into a bounded-memory SHA-256 calculation, counts bytes, checks EXE/MSI/PKG signatures or DMG koly trailer, and verifies the expected digest. It never sends bytes through an HTTP app endpoint. Storage outages remain uploaded/retryable; invalid content becomes failed and requires a replacement upload. Each run handles up to 100 uploaded records; repeat until drained. Do not expose this CLI as a public endpoint.
6. Review Release Assets for verified status and notes in both locales, explicitly mark ID/EN reviewed, select active, then publish. Both OS builds must be verified. If duplicates exist, use Assets To Publish to select exactly one verified candidate for each OS/architecture; both Windows and macOS remain required. Empty selection preserves the previous all-verified behavior. The server rejects foreign-release, unverified, incomplete and duplicate candidates. Candidate selection is versioned and audited. Publication snapshots exact verified asset IDs, so late uploads cannot silently enter the approved set. Asset metadata is immutable even for admin REST calls; the internal workflow capability is server-only.
7. Publish a reviewed CMS page with key download in both locales to expose /id/download and /en/download. Pages use existing CMS metadata, canonical/hreflang and sitemap handling. New UI labels are visibly unreviewed samples; release notes use CMS localization with no fallback.
8. Retire a published release by saving lifecycle=retired as published. It disappears from current cards and redirects immediately; draft retirement does not change the published version. Retire before replacement when an old version must no longer be downloadable. Records and object versions are retained for audit; deletion through CMS APIs is disabled.

## Delivery and failure semantics

Public queries explicitly project only active, published stable releases, reviewed locale notes and snapshotted verified assets. Latest means most recently first-published release per OS/architecture (not semantic-version sorting). Preview channel is never publicly selected. Up to 100 latest releases and 200 approved asset IDs per release are inspected (other historical candidates do not displace the approved selection); larger catalogs require pagination before approaching those limits.

GET /api/downloads/[assetId]?locale=id|en requires no account. It rechecks current eligibility and versioned storage size, then returns an empty 302 response to a 60-second signed storage GET with attachment disposition. It never reads the binary. Missing/retired/unapproved IDs return 404; storage/configuration errors return 503, localized sample text and Retry-After:60. Invalid request returns 400. API responses and signed redirects are no-store/noindex. Existing signed URLs can remain usable for at most 60 seconds after retirement; immediate revocation requires provider intervention. URLs are bearer credentials: avoid access-log query capture at storage/proxy layers.

Admin mutations require exact same origin, active Super Admin and JSON. Persistent database counters cap 10 upload creations/admin/hour and 500 control requests/admin/hour. Sessions are owner-bound and part URLs are key/upload/part/length scoped. Signed URL replay can only overwrite a part in the same incomplete upload; final verified versions are pinned. Invalid/missing parts can be retried. Expired sessions abort on the next action; automatic abandoned-upload cleanup is a mandatory bucket lifecycle prerequisite. Cancellation after completion is not retirement.

If the app completion response is lost after its DB update succeeded, Retry detects uploaded/verified state and finishes without a replacement. If the storage completion response or following DB write is lost, server state may remain pending: never blindly activate that orphan. An operator must inspect DB and exact storage version references before deciding whether to cancel/replace and reconcile unreferenced private objects. An uncertain storage operation must not be assumed to have failed. App credentials cannot delete versioned objects. Audit events record workflow metadata changes and publication/retirement; no IP, user-agent or customer identity is collected, and aggregate download events are not enabled.

Magic/digest checks establish format and integrity, not code-signing/notarization, malware safety or truthful architecture. Trusted build provenance, signing/notarization inspection and real supported OS installation are release-owner gates. Verification CLI is a manually invokable batch; production scheduling, alerting and credentials separation belong to hosting operations.
